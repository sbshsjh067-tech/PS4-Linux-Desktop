### Q3 — What "both layouts" means (and the fate of BOOT-003)

There are **two distinct, real, shipped layouts**, and they differ in *who delivers the kernel*:

**Layout A — self-contained USB** (proven by `ps4-multiboot/scripts/make-usb.sh`):
```
MBR
├─ p1  FAT32  label PS4BOOT   (512 MiB, boot flag)  ← bzImage + initramfs.cpio.gz
└─ p2  ext4   label <NAME>-PS4                     ← root filesystem
```
The PS4 payload reads the kernel off the FAT32 partition; the initramfs finds the root by **label**
(`LABEL=<NAME>-PS4`), *not* by `root=` in bootargs. The published `bootargs.txt` contains no `root=` at all.

**Layout B — kernel on the console, USB = root only** (proven by `X-F1REBALL-X/PS4-Linux`):
kernel + initramfs are FTP'd to `/data/linux/boot/`, the USB carries only the root filesystem.

So: **"FAT32-boot-partition" = the payload's kernel-delivery partition, not `/data/`.** Both are supported
paths; the product must let the user pick one and must never mix them.

**Therefore BOOT-003 is downgraded and rewritten.** My original wording ("USB bzImage silently overrides
`/data/linux/boot`") came from a community note about one specific loader version [`S14`] and I presented it
as a general rule. The loader repositories are 404, so **I cannot verify the precedence for the loader you
are using**, and I will not keep a rule I cannot check. Replacement rules:

1. **Layout must be explicit** in `profile.yaml` (`boot.layout: usb_fat32 | internal_ftp`).
2. **Never leave a kernel in both places.** Pre-flight check: if `bzImage` exists on the FAT32 boot
   partition *and* `/data/linux/boot/bzImage` exists → refuse and ask the user which one is authoritative.
3. **Checksum the kernel you ship** (`sha256`) and print it in the boot log window; the manifest must
   travel with the image (`kernel.info` equivalent).
4. **Keep the guard that is verifiable today:** md5/sha verification after writing, and the
   fake-capacity check from `make-usb.sh` (partition 1 must still be `vfat` after partition 2 is formatted —
   catches counterfeit sticks).

**One question back to you** (it changes T-004's first line of code): in your current app, `bzImage` +
`initramfs.cpio.gz` are written to the USB **root** — is that root the FAT32 partition or the ext4 root?
If it is ext4, the payload may not be able to read it at all, which would look exactly like BOOT-001/B0OT-002.
